# บันทึกวิธีตรวจ OCR และผลที่พบ

วันที่บันทึก: 15 ตุลาคม 2026

**เป้าหมาย:** ตรวจว่าข้อความที่ Typhoon OCR อ่านจาก PDF ตรงกับต้นฉบับแค่ไหน โดยเฉพาะภาษาอังกฤษ แล้วใช้วิธีเดียวกันเปรียบเทียบโมเดลอื่นก่อนเลือกใช้งาน

**สถานะตอนนี้:** ตรวจโครงสร้างไฟล์แล้ว และพบข้อความอังกฤษผิดที่หน้า PDF 36 แต่ยังไม่มีคะแนน CER/WER จริง เพราะยังไม่ได้เตรียมข้อความเฉลยที่คนตรวจครบหน้า

**การเก็บประวัติ:** หลังทราบข้อผิดพลาด เจ้าของอนุญาตให้ commit/push งานและข้อมูลดิบเพื่อเก็บเรื่องนี้ไว้ การอนุญาตนี้ไม่ใช่การยืนยันว่า OCR ผ่าน หน้า 36 และคะแนนประเมินจริงยังต้องดำเนินการต่อ

## 1. เราทำอะไรไปแล้ว

เจ้าของโปรเจกต์รัน `typhoon-ai/typhoon-ocr1.5-2b` บน Colab ตาม [notebook 03](../Backend/notebooks/03_typhoon_ocr_colab.ipynb) โดยใช้วิธีนี้:

```text
PDF → แปลงทีละหน้าเป็นภาพ → โมเดลอ่านข้อความ
    → เก็บข้อความพร้อมภาษา/ชื่อ PDF/เลขหน้า → บันทึก JSONL, TXT และ MD
```

โมเดลอ่านทั้งหน้าแล้วสร้างข้อความออกมา ผลจึงอาจมีทั้งตัวอักษรอ่านผิด ข้อความหาย หรือข้อความที่สร้างเพิ่ม เราเปลี่ยนจาก pipeline ดึงข้อความเดิมมาใช้ OCR และเก็บ notebook การทดลองเดิมไว้เป็นประวัติ

## 2. ใช้วิธีตรวจอะไรบ้าง

| วิธี | ทำอย่างไร | บอกอะไรได้ |
|---|---|---|
| ตรวจโครงสร้าง | อ่าน JSONL ทุกบรรทัด ตรวจเลขหน้า ภาษา ชื่อไฟล์ และข้อความว่าง | ไฟล์ครบและจัดข้อมูลถูกหรือไม่ |
| ตรวจการบันทึก | สร้าง TXT/MD กลับจาก JSONL แล้วเทียบกับไฟล์ที่นำเข้า | ทั้งสามไฟล์เก็บข้อความตรงกันหรือไม่ |
| คัดหาหน้าที่น่าสงสัย | เทียบข้อความ OCR กับข้อความที่ PyMuPDF ดึงจาก PDF | ช่วยหาหน้าให้คนตรวจเพิ่ม ไม่ใช่คะแนนความถูกต้องจริง |
| ตรวจภาพต้นฉบับ | เปิดภาพหน้า PDF ที่สงสัยแล้วอ่านเทียบกับ OCR | ยืนยันได้ว่าข้อความจุดนั้นผิดจริงหรือไม่ |
| วัด CER/WER | เทียบ OCR กับเฉลยที่คนตรวจครบหน้า | เตรียม notebook แล้ว แต่ยังไม่ได้วัดกับเฉลยจริง |

ข้อความที่ดึงจาก PDF ใช้ช่วยตรวจได้ แต่ต้องอ่านภาพก่อนถือว่าเป็นเฉลย เพราะตัวดึงข้อความอาจมีปัญหาลำดับการอ่านหรือข้อความขาดได้เช่นกัน

## 3. ผลจริงที่ยืนยันแล้ว

| รายการ | ภาษาไทย | ภาษาอังกฤษ |
|---|---|---|
| จำนวนหน้าที่นำเข้า | 44 หน้า | 39 หน้า |
| เลขหน้าใน JSONL | ต่อเนื่อง 1–44 | ต่อเนื่อง 1–39 |
| จำนวนอักขระในข้อความ OCR | 84,305 | 104,900 |
| หน้าที่ข้อความว่าง | ไม่พบ | ไม่พบ |
| หน้าที่ตั้งธง `possibly_truncated=true` | ไม่พบ | ไม่พบ |
| TXT/MD ตรงกับ JSONL | ตรง หลังปรับรูปแบบการขึ้นบรรทัด | ตรง หลังปรับรูปแบบการขึ้นบรรทัด |
| คะแนน CER/WER จากเฉลยคนตรวจ | ยังไม่ได้วัด | ยังไม่ได้วัด |

**จำนวนหน้าครบไม่ได้แปลว่าข้อความถูกทุกคำ** และการไม่มีธง truncated ไม่ได้รับรองว่าโมเดลอ่านข้อความครบ

### ข้อผิดพลาดภาษาอังกฤษหน้า PDF 36

เทียบกับภาพต้นฉบับแล้วพบสองจุดสำคัญ:

1. ต้นหน้าจริงเป็นข้อความต่อจาก Section 83 แต่ OCR แทนด้วยย่อหน้าที่เพิ่มหัวข้อ Section 83 และมีเนื้อหาผิดจากต้นฉบับ
2. Section 84 ใน PDF ระบุ `five million Baht` แต่ OCR อ่านเป็น `three million Baht`

จึงยังไม่ควรใช้ผลอังกฤษชุดนี้เป็นข้อความที่ผ่านการตรวจแล้ว และยังไม่ commit/push ตามเงื่อนไขเดิมที่ให้ตรวจผ่านก่อน เก็บ OCR ดิบไว้โดยยังไม่ได้แก้ข้อความทับ

ภาษาไทยหน้า 1 มีคำบรรยาย `<figure>` ที่ยังต้องตรวจเทียบภาพ ไม่ควรถือว่าคำบรรยายที่โมเดลสร้างถูกต้องโดยอัตโนมัติ

รายละเอียดการตรวจเดิม: [ภาษาไทย](001-typhoon-thai-ocr.md) และ [ภาษาอังกฤษ](002-typhoon-english-ocr.md)

## 4. วัดระดับตัวอักษรกับระดับคำต่างกันอย่างไร

**ระดับตัวอักษร:** ดูว่าตัวอักษร ตัวเลข หรือเครื่องหมายต่างจากเฉลยอย่างไร ใช้ CER หรือ Character Error Rate

```text
CER = (จำนวนตัวอักษรที่แทนที่ + ลบ + เพิ่ม) / จำนวนตัวอักษรในเฉลย
```

**ระดับคำ:** ดูคำทั้งคำ ถ้าตัวสะกดผิด คำนั้นก็ไม่ตรง ใช้ WER หรือ Word Error Rate โดยเปลี่ยนหน่วยในสูตรเป็นคำ

เราใช้ CER ทั้งไทยและอังกฤษ ส่วน WER ใช้เพิ่มเฉพาะอังกฤษ เพราะวิธีแบ่งคำด้วยช่องว่างใช้กับภาษาไทยตรง ๆ ไม่ได้

คะแนนยิ่งต่ำยิ่งดี แต่ไม่ได้บอกความร้ายแรงของคำที่ผิด คำอย่าง `not` หรือจำนวนเงินอาจผิดเพียงเล็กน้อยในเชิงจำนวนตัวอักษร แต่ทำให้ความหมายเปลี่ยนมาก

### ตัวอย่างคำนวณสั้น ๆ — ไม่ใช่คะแนนหน้า 36

```text
เฉลย: five million Baht
OCR:  three million Baht
```

ทดลองคำนวณสองข้อความนี้ด้วย JiWER 4.0.0 ได้:

| ค่า | ผลตัวอย่าง |
|---|---|
| ตัวอักษรอ้างอิง รวมช่องว่าง | 17 |
| Character edit errors | 4: แทนที่ 3 และเพิ่ม 1 |
| CER | 4 / 17 = 23.53% |
| WER | 1 / 3 = 33.33% |

ตัวอย่างนี้ใช้แค่สามคำเพื่ออธิบายสูตร ไม่ใช่ผลของข้อความครบหน้า และใช้แทนคะแนนทั้งเอกสารไม่ได้

## 5. อ่านเปอร์เซ็นต์ในบทความอย่างไร

บทความ LlamaIndex อธิบาย accuracy แบบนับตัวอักษรที่ถูกหารด้วยจำนวนตัวอักษรอ้างอิง ตัวอย่างด้านล่างแสดงผลเชิงจำนวน **เมื่อมีตัวอักษรอ้างอิง 1,000 ตัว** ตามนิยามการนับนั้น:

| Accuracy ตัวอย่าง | ตัวอักษรที่นับว่าถูก | ตัวอักษรอ้างอิงที่นับว่าไม่ถูก |
|---|---|---|
| 90% | 900 | 100 |
| 95% | 950 | 50 |
| 98% | 980 | 20 |
| 99% | 990 | 10 |
| 99.5% | 995 | 5 |
| 99.9% | 999 | 1 |

**ตารางนี้ไม่ใช่ผลของโปรเจกต์เรา และไม่ใช่เกณฑ์รับรองว่าเอกสารผ่าน** เราไม่ยกคำประเมินคุณภาพในบทความมาเป็นข้อสรุปว่าเอกสารนี้พร้อมใช้

ต้องแยกหน่วยตัวอักษรกับคำด้วย จำนวนข้อผิดพลาดต่อเอกสาร 1,000 คำประมาณจาก character accuracy ตรง ๆ ไม่ได้ หากไม่รู้ความยาวข้อความและวิธีนับ

ใน notebook เรารายงาน **CER/WER** ซึ่งรวมข้อความที่โมเดลเพิ่มด้วย ค่าอาจเกิน 100% จึงไม่เปลี่ยน `100% − CER` เป็น accuracy ทางความหมาย และไม่สรุปว่าจำนวนเงินถูกเพียงเพราะคะแนนรวมดูดี

## 6. วิธีที่เตรียมให้รันต่อ

ใช้ [notebook 04](../Backend/notebooks/04_ocr_evaluation.ipynb) บน CPU ได้ โดยไม่ต้อง OCR ซ้ำ มีเพียง:

- CER และ WER อังกฤษ ทั้งรายหน้าและรวมชุดที่วัด
- กราฟ CER รายหน้า 1 รูป แยกโมเดลเพื่อดูหน้าที่ผิดเยอะ
- ข้อความ diff เพื่อเห็นคำที่เพิ่ม ลบ หรือเปลี่ยน
- เลือกบันทึก `summary.csv`, `by_page.csv` และกราฟได้

คะแนนรวมใช้จำนวน edit errors รวม หารความยาวเฉลยรวม ไม่ใช่เฉลี่ยเปอร์เซ็นต์ทุกหน้าเท่ากัน

ก่อนเทียบ ใช้กติกา `content_v1` เหมือนกันทั้งสองฝั่ง: Unicode NFC, ยุบช่องว่าง, ตัดแท็กเลขหน้าและเครื่องหมาย Markdown บางแบบ โดยเก็บตัวเลข คำปฏิเสธ ตัวสะกด และคำบรรยาย figure ไว้ กติกานี้ยังไม่รองรับ Markdown ทุกกรณี

ทดสอบการทำงานของ notebook แล้ว ได้แก่ โหลดข้อมูลอังกฤษจริง กรณีไม่มีเฉลย การคำนวณ/กราฟ/ส่งออกด้วยข้อความจำลองแยกจากข้อมูลจริง และการหยุดเมื่อโมเดลใดขาดหน้าที่ใช้เทียบ **การทดสอบโค้ดผ่านไม่ใช่การยืนยันคุณภาพ OCR**

ตอนบันทึกเอกสารนี้ `Data/ground_truth/` มีเพียง README ยังไม่มีไฟล์เฉลย และไม่พบรายงานคะแนนจริงจาก notebook 04 ในโปรเจกต์

## 7. ทำอะไรต่อ และจะตัดสินใจเปลี่ยนโมเดลอย่างไร

1. เตรียมเฉลยอังกฤษครบหน้า เริ่มหน้า 36 แล้วเพิ่มหน้า 1, 10, 20, 39 ตาม [วิธีทำ Ground truth](../Data/ground_truth/README.md)
2. รัน notebook 04 เพื่อได้คะแนนและ diff ของ Typhoon บนชุดนี้ก่อน
3. หากลองโมเดลอื่น ให้ใช้ PDF หน้าเดิม เฉลยเดิม และกติกาเตรียมข้อความเดิม เปรียบเทียบ CER/WER พร้อมตรวจจำนวนเงิน เลขมาตรา และคำปฏิเสธ
4. ก่อนเลือกโมเดลสุดท้าย ลองหน้าใหม่เพิ่มที่ไม่ได้ใช้ปรับวิธี เพื่อดูว่าผลดีขึ้นนอกหน้าที่รู้ปัญหาด้วย

ความตั้งใจของเจ้าของคือเลือกโมเดลที่อ่านภาษาอังกฤษได้แม่นขึ้นถ้า Typhoon มี error มาก ขณะนี้ยังไม่ได้ทดลองโมเดลทดแทน และยังสรุปไม่ได้ว่า Typhoon อังกฤษผิดเยอะทั้งเล่มจากหน้า 36 เพียงหน้าเดียว
